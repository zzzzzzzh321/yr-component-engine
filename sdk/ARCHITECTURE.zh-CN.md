# Mod SDK 架构与扩展指南

一个作品选择一个可选的 WebAssembly 功能组件，参考组件包含各功能代码，通过作品 INI 选择本局启用项。护盾和弹药是同一组件中的两个功能模块。原版不声明组件，走原有引擎流程。

## 从引擎到功能的调用路径

```text
引擎原有 Rules / 对象构造 / 伤害 / AI 更新阶段
  → src/mod_sdk.rs：稳定入口
  → assets.rs：接纳作品或恢复原组件
  → program.rs：冻结配置、准备请求、调用运行时
  → sdk/runtime：创建新实例、限制执行、校验返回计划
  → 插件 lib.rs：WIT 导出与消息解码
  → 插件 component.rs：按回调分派
      ├─ features/shield：护盾与过载
      └─ features/ammo.rs：武器弹药策略
  → 引擎 simulation.rs：在原阶段提交计划
```

插件通过 `support` 调用只读宿主服务，宿主适配位于引擎的 `host.rs`。配置仍使用引擎已有的 INI 读取器，伤害数值计算仍调用引擎已有的公共算法；插件不复制解析器或伤害内核。

## 每一层负责什么

| 层 | 职责 | 不应放入的内容 |
| --- | --- | --- |
| `sdk/api` 与 `sdk/wit` | 双方约定的请求、计划、版本、能力边界 | 具体护盾或弹药规则 |
| `sdk/runtime` | 组件加载、受限执行、消息校验 | 游戏对象、INI 业务解释 |
| 引擎 `mod_sdk/program.rs` | 原始组件、摘要、manifest、冻结配置；可重建的执行缓存 | 具体功能算法、真实生命值副本 |
| 引擎 `mod_sdk/assets.rs` | 资源声明、摘要验证、存档组件身份匹配、重建 Rules 派生策略 | 回调算法 |
| 引擎 `mod_sdk/host.rs` | 可信的配置读取、目录和数值服务 | `ShieldType`、`VeraOverload` 等功能语义 |
| 引擎 `mod_sdk/simulation.rs` | 转换当前游戏事实、调用组件、提交结果或记录故障 | 另写一份护盾逻辑 |
| 插件 `lib.rs` | 对接 WIT、解码、检查回调名称 | 功能配置和游戏算法 |
| 插件 `component.rs` | 声明本组件、配置封装、显式调用顺序 | 护盾如何吸收伤害 |
| 插件 `features/*` | 各自的配置和决策；有状态功能管理自身状态 | 直接修改引擎对象、联网或读取磁盘 |
| 插件 `support/*` | 通用宿主调用、数值编码 | 特定功能的键名和默认值 |

引擎根入口通过重导出保留原有路径，调用方继续使用 `mod_sdk::Program`、`mod_sdk::attach_entity` 等。`Program` 的字段保持私有。现有公开的 `Program::load` 仍保留；需要类型目录的正式加载路径使用 `load_with_types`。

## 配置、状态和缓存各有一个所有者

- **功能配置**：护盾模块拥有护盾目录、全局默认值、对象/弹头绑定和过载设置；弹药模块拥有武器成本表。组件层只组合它们。配置阶段结束后冻结，对局中只读。
- **对象状态**：护盾模块拥有护盾值、四个恢复倒计时、热量和过载倒计时。引擎仅保存不透明字节，不另维护一套护盾状态。弹药策略无独立对象状态，真实弹仓仍由引擎原有弹药模块拥有。
- **显示数据**：插件输出通用进度条和染色投影，由引擎显示；投影不作为游戏状态权威。
- **派生策略**：Rules 的武器策略来自冻结组件配置；读档后重新绑定，不成为第二份可编辑配置。
- **执行缓存**：编译后的 Wasm 可丢弃并重建，不进存档或联机校验。每次回调仍创建新的实例，不依赖 Wasm 全局变量保留状态。

组件层是功能启用的唯一所有者：`[VeraFeatures]` 三个开关默认关闭，逐 Rules 层读取，最终校验 Overload 依赖 Shield。配置分派顺序为：读取选择，最终阶段配置已开启的弹药，再配置护盾，全部成功后才发布冻结结果。护盾目录在未开启时仍累积，以支持后层开启。`weapon_resource` 在 AresAmmo 关闭时返回 None；Shield 关闭时对象事件返回空状态和空显示投影。Overload 的启用布尔值显式传给护盾算法，不在功能配置中另存一份。战斗各阶段、计时器和随机数顺序沿用现有调用点。

## 添加下一项功能

先判断现有接口是否已经提供所需事实和可提交结果。

1. **已有能力足够**：在 `features` 增加本功能模块，使其拥有配置和决策；在 `component.rs` 的配置阶段和相关回调中显式接入。功能启用项写入 INI，并随冻结配置保存；不要用 Cargo feature 代替玩法选择。`lib.rs`、Wasmtime 运行时和引擎通常无须改动。
2. **需要新的通用能力**：先扩展 `sdk/api` 的上下文/返回计划及其验证，再在引擎真正拥有该状态的模块接入。只有新增宿主服务时才需要改 WIT 导入。引擎保留通用操作，兼容写法与功能算法留在插件。
3. **同一回调有多项功能**：在组件层明确先后关系、伤害如何传递和显示如何合并。当前没有通用多功能状态容器，也没有自动冲突合并。新增第二项有状态功能时，应先设计有版本的状态封装，再增加读写双方与存档测试，不能直接覆盖另一功能的字节。

例如修改“每发消耗两颗弹药”为“消耗三颗”，修改 `features/ammo.rs` 的策略或其配置解释，再构建组件即可。开火检查、扣弹、装填仍走原引擎所有者。若希望实现“护盾受到伤害后给另一辆车回血”，目前的返回计划无法表达它；应设计受校验的通用跨对象效果，不能绕过权限直接写对象。

不为两个功能引入动态注册总线、依赖解析或通用继承框架。多个作者可以维护各自的功能目录；一个作品的组件层负责选择、编译和确定顺序。有第二个独立组件真正需要共用代码时，再把 `support` 提成单独的 SDK guest crate。

## 兼容边界

统一参考组件声明 `vera.reference-gameplay` 0.3.0，config_version=3，state_version=1；API v1、WIT 包名不变，组件包含五种回调。冻结配置新增 features，旧状态字段和浮点位编码不变。功能选择与配置原始字节一起进入存档和联机校验，不接受对局中读取当前 INI 来覆盖。

旧 0.1/0.2 二进制组件保持各自原有行为，现有通用宿主仍可加载。它们不认识新开关，不能靠给旧组件添加新 INI 来获得按需选择。新旧配置格式有意不同，不进行跨组件迁移。

源文件搬动或重新编译可能改变组件的 SHA-256。读档要求作品资源与存档中的组件摘要一致，所以旧存档仍应保留并使用原来的组件文件。相同数据格式不代表可以把旧局组件直接换成新构建；本版没有热替换或状态迁移。

验证入口包括插件行为测试、真实 Wasm 与原生配置读取器的集成测试，以及原版/兼容护盾/过载护盾/弹药/零售地图的正式引擎探针。`sdk_ini_selection_is_layered_frozen_and_restored_with_the_program` 通过真实 INI 读取器检查分层开关、依赖、禁用、保存与恢复。保留的 `sdk_refactor_preserves_` 测试仅比较旧 0.1/0.2 制品的字节。构建与命令行说明见 [中文 README](README.zh-CN.md) 和 [弹药示例](plugins/shield/AMMO.zh-CN.md)。

以上仍是实验版 SDK，不代表完整 Ares/Phobos 兼容，也没有完成大规模性能和各桌面平台的验证。
